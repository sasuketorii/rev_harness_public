# 開発憲法を適用する

## このリポジトリでの位置づけ

このリポジトリの受け入れ正本は `docs/manual/verification-truth-matrix.md` であり、
本憲法はその下で働く一般的な開発規範である。役割定義は `docs/roles/*.md`、
共有ルールは `.agent_rules/RULES.md` とその配下、リポジトリ横断の不変条件は
`AGENTS.md` と `docs/canonical-invariants.md` が正本を持つ。本憲法とこれらの
文書が具体的な手続き(dual-LGTM のゲート機構、role 名、メトリクス項目、
承認境界など)で異なる場合は、当該具体的手続きの正本が優先する。本憲法は、
それらの具体的手続きが存在しない場合の一般的な判断基準、または既存正本を
読み解く際の上位原則として使う。

### 既知の相違: light task class のレビュワー要件

憲法 (`references/constitution.md` §5.1 / §6.2 / §9.1) は、最低リスク層を含む
すべてのリスク層でレビュワー LGTM を完了条件として要求する。一方、このリポジトリ
の受け入れ正本 `docs/manual/verification-truth-matrix.md` は `light` task class を
定義し、そこではレビュワーも LGTM ゲートも要求せず、orchestrator が自己クローズ
できる (`verification-truth-matrix.md` の task class 表と `docs/roles/orchestrator.md`
を参照)。

これは表現の揺れではなく、実際の相違である。**このリポジトリでは truth matrix の
定義が優先する。** 根拠は `AGENTS.md` §Read Order の衝突解決規則で、より具体的な
正本が優先し、かつ light class の定義は安全・証跡・決定的受け入れのいずれも
弱めていないためである (light class に該当するのは、決定的チェックだけで
受け入れ可能な低リスク面に限られる)。

したがって本憲法の「全層でレビュワー必須」は、このリポジトリでは
**standard 以上の task class に適用される**と読むこと。light class に対して
レビュワーを要求するために本憲法を引用してはならない。逆に、light class に
分類してよいかどうかの判定自体は truth matrix と分類器が持つ。

## 正本を読む

作業を開始する前に [references/constitution.md](references/constitution.md) を全文読む。
このファイルを詳細規範の正本として扱い、同じ規範を別ファイルへ複製しない。

## 適用する

1. 要求、対象範囲、既存実装、制約、リスクを根拠付きで把握する。
2. 憲法の必達要件を、今回の作業に対する具体的な受け入れ条件へ変換する。
3. リスクに応じて作業者とレビュワーを分離し、必要な専門レビューまたは最終確認へエスカレーションする。
4. 既存実装と公式資料を先に調査し、二重開発、陳腐化した設計、非推奨構成を避ける。
5. 最小で一貫した変更を実装し、性能、安全性、正確性、保守性を検証する。
6. テスト、静的検査、計測、差分、公式資料など、結論を支える証拠を残す。
7. レビュー指摘を修正した後は再レビューを行い、レビュワーの最終LGTMで閉じる。
8. 完了条件を満たした事実、実行した検証、残存リスク、未実施事項を区別して報告する。

## 判断する

- 複数の要件が競合する場合は、正本の「矛盾時の優先順位」に従う。
- 要件を満たせない場合は、黙って緩和せず、例外の理由、影響、代替策、期限、承認者を明示する。
- 実測または確認できない品質を、推測だけで「安全」「高速」「完了」と断定しない。
- コーダーの修正報告を完了とみなさず、最終レビュー結果を確認する。
