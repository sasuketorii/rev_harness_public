# セマンティックインデックスが存在しない理由

English original: [docs/architecture/why-no-semantic-index.md](../../architecture/why-no-semantic-index.md)

RevHarnessはかつてセマンティックなコードインテリジェンスのサブシステムを搭載していました。それは削除されました。このページは、それが何だったのか、なぜなくなったのか、そして何がその代わりになったのかを記録します——「試して、やめた」という事実は、沈黙よりも読者の役に立ちますし、2026年にエージェントハーネスを評価する人なら、なぜこのハーネスにベクトルインデックスがないのかを妥当な疑問として持つはずだからです。

## それは何だったか

ハーネスの寿命の大半において、コンテキスト取得はセマンティック層を通っていました。

- プロジェクトごとのSQLiteデータベース(`semantic.db`)。リポジトリの `project_id` で名前空間分けされ、レジストリ・シンボル・全文検索(FTS)・意思決定の各テーブルを保持。
- **tree-sitter** によるシンボルインデックス。コードベースを解析し、問い合わせ可能なシンボルグラフにしていた。
- **MCPサーバー**。`sem.*` というツール群——`sem.context.top_k`、`sem.capsule`、`sem.search`、`sem.admin.gc`——をJSON-RPC経由で公開し、エージェントがそれを呼んでいた。
- **コンテキストカプセル**。約220トークンに圧縮された要約で、生のファイル内容の代わりにエージェントへ渡していた。
- 2つのRustクレート(`semantic-mcp`、`tree-sitter-index`)、ブートストラップ/起動スクリプト、専用のCIゲート、鮮度(staleness)の契約、データベースのロックプロトコル。

その前提はありふれたもので、当時としては妥当なものでした。大きなリポジトリはエージェントのコンテキストウィンドウを圧迫する。だからインデックスを構築し、関連する断片を取得し、圧縮されたカプセルをエージェントに渡す、というものです。

## なぜ削除されたか

削除は、ある日苛立って一気にやったものではなく、2段階に分けて意図的に行われました。

**Stage 1(v0.2.0)—— オプトインのアドオンへの降格。** Coreはセマンティックのmcpサーバーを自動起動しなくなりました。新規アダプター(adopter)はデフォルトでcoreのみになりました。セマンティック用のクレートはワークスペースに残りましたが、明示的なアドオンゲートを通してのみビルド・テストされるようになりました。決定的に重要なのは、このリリースで**計測期間**が開始されたことです。インデックス維持コスト、アドオンゲートの利用状況、レビューサイクルのコスト、そしてこのサブシステムを別プロジェクトへ切り出すための基準です。

**Stage 2(v0.3.0)—— 完全な削除。** 計測結果は「維持しない」方向を示しました。サブシステムは削除されました。両方のクレート、MCPのワイヤーサーフェス、カプセル、FTS5テーブル、セマンティック用のCIゲート、アドオン階層、セマンティック用のスキルとルールモジュール、そしてドキュメントです。この変更は約2,000行を追加する一方で、およそ**229ファイルにわたる42,900行**を削除しました。

この判断を後押ししたのは3つのことです。

1. **インデックスは鮮度を保ち続けなければならず、鮮度はfail-closedなサーフェスである。** 古びたインデックスは、インデックスがないよりも悪いものです——自信満々に昨日の構造を返してきます。これを防ぐには鮮度の契約、staleness gate、そしてインデックスが遅れているという理由でハーネスが処理を拒否する失敗モードが必要でした。これはコミットのたびに課される永続的な維持コストであり、それが買っているのは作業そのものの正しさではなく、検索層だけの正しさです。
2. **エージェント的な検索が追いついた。** 整理されたリポジトリに対して、自分のクエリを自分で反復改善できるエージェントが `rg` を使うと、事前計算されたインデックスなしで必要なものを取得できることが分かりました。エージェントは、自分が必要だと判断した順序で、自分が必要だと判断したものを読みます。固定のtop-k取得はそのようには適応できません。
3. **カプセルは、間違った方向に情報を失っていた。** ファイルを220トークンの要約に圧縮すると、まさに——off-by-oneのバグ、ガード節、変わったearly return——そのファイルを変更しようとしているときに重要になる細部が失われます。コンテキスト予算は節約できても、読む価値がある部分を取り除いてしまっていました。

この削除は、ハーネスの価値を担っている部分——決定論的なゲート、二重レビューの証拠要件、インストールのsmoke gate——には触れないよう、意図的に範囲を絞って行われました。

## 何がその代わりになったか

的を絞った検索と生の読み込みを、リポジトリにチェックインされたインデックスマップで導くという方式です。

- **`rg` / エージェント的検索** — エージェントが自分自身のクエリを立て、練り直します。
- **`INDEX_MAP` 文書**(`docs/INDEX_MANIFEST.md`、`docs/INDEX_MAP-*.md`) — リポジトリのどこに権威(authority)があるかを人手でまとめたマップです。これらは**ナビゲーションの補助であり、受け入れ判定の真実ではありません**。`scripts/ci/index-map-check.sh` がこれらのドリフトを防ぎますが、何かがこれらの言い分だけを根拠に作業を受け入れることはありません。
- **`.shared/project_id`** — 状態・キャッシュ・証拠が紐づく永続的な識別子です。これは削除を生き延びました。もともとセマンティックなものではなかったからです。

## これがあなたにとって何を意味するか

- 実行・ブートストラップ・同期を維持すべき**ベクトルデータベースも、埋め込みモデルも、MCPサーバーもありません**。インストールにインデックス構築のステップはありません。
- コンテキストの質は、リトリーバルパイプラインがどれだけチューニングされているかではなく、あなたのリポジトリがどれだけナビゲート可能で、あなたのインデックスマップがどれだけ正直かに依存します。
- もしあなたのユースケースが本当にセマンティック検索を必要とするなら、このハーネスはそれに敵対的ではありません——単に提供していないだけです。自分自身のMCPサーバーを配線してください。ラッパー層は、エージェントがどんなツールを持っているかを気にしません。
- もし元のサブシステムが欲しいなら、それは履歴から消えたわけではありません。0.3.0より前のタグにピンするか、上流リポジトリのgit履歴から削除されたクレートと配線を復元してください。それを不可能にするような書き換えは行われていません。

引退したinvariant(`I-2`、`I-13`、およびアドオン用invariantの `Addon-I-2`、`Addon-I-2b`、`Addon-I-13`)は、
[`docs/canonical-invariants.md`](../../canonical-invariants.md)(英語) にトゥームストーン(墓標)として残されています。それらのIDは二度と再利用されないため、古い参照は、番号を振り直された別のルールへ誤って解決されるのではなく、明示的に「これは削除された」という結果になります。
