# RevHarness

**AIコーディングエージェントに、自信満々なだけの成果物ではなく、検証可能な成果物を出させるための、ミドルクラスでリポジトリ内完結のハーネス。**

English original: [README.md](../../README.md)

RevHarnessはリポジトリの内側に置かれ——デーモンとしてでも、サービスとしてでもなく——エージェント駆動の開発で失われがちな4つのことを強制します。

- **受け入れ判定は機械的に行う。**「完了」とは、名前の付いた決定論的チェックがゼロ終了し、成果物(artifact)を残したことを意味します。エージェントが「終わった」と言うことは証拠になりません。
- **呼び出しは単一のエントリポイントを通す。** すべてのエージェント呼び出しは、そのロールに応じた reasoning effort と web-search ポリシーを固定し、最低モデルを強制し、その設定を広げようとするコマンドライン上の試みを取り除く/拒否するラッパーを経由します。ベンダーCLIを直接呼べばこれは全部素通りします——このハーネスは協力的なユーザーの行動を制約するものであり、セキュリティ境界ではありません。
- **レビューは成果物(artifact)を残す。** フェーズを進めるには、判定(verdict)を伴う2つのレビューファイルがディスク上に存在すること、加えてゼロ終了した smoke run があることが必要です。ハーネスはそれらの成果物が存在し、必要な内容を記述していることをチェックします。どのモデルがそれを書いたかまでは——証明しませんし、できません。
- **失敗は閉じる(fail-closed)、開かない。** あることが安全かどうかハーネスが判断できない場合、処理は停止します。破壊的な操作には、毎回明示的なオプトインフラグが必要です。

**「ミドルクラス」は控えめな言い方ではなく、正確な表現です。** これは置いたら忘れられる類のものではありません。シェルスクリプト77本、テスト103本、3クレート構成のRustコア、そしてエージェントが従うことを前提とした規約群です。中身はすべて開いて書き換えられるプレーンテキストで、デーモンもサービスも、信用を要求してくるバイナリもありません。しかし相応の面積があり、採用するとはその面積を引き受けるということです。一晩で把握できるものが欲しいなら、これは向いていません。受け入れ判定のモデルが欲しくて、それを強制する機構を運ぶ覚悟があるなら、それがこのトレードです。

**スコープ: これはバックエンド用ハーネスです。** 迅速に、かつ自分で責任を持てる品質でバックエンド・システムコードを生み出すために存在します。フロントエンドハーネスではありません——フロントエンド作業に必要なデザインシステム、コンポーネント調達、視覚的な判断といった仕組みはここにはなく、それを追加することも最初から目指していません。

## このハーネスが解決する問題

有能なエージェントを実際のコードベースに向けると、4つの失敗モードが確実に現れます。

| 失敗モード | どう見えるか | RevHarnessがすること |
|---|---|---|
| **再現不能な受け入れ判定** | 同じ依頼でも結果が毎回違い、「LGTM」が単なる口約束になる | `docs/manual/verification-truth-matrix.md` が唯一の受け入れ判定の権威。完了を主張できる根拠は決定論的チェックの成果物だけ |
| **境界の侵食** | エージェントが静かにスコープを広げる、あるいはレビュワーが実装を始めてしまう | すべての呼び出しがロール固定のラッパーを通り、effortとsearchポリシーを固定し、最低モデルを強制し、それを広げようとするコマンドライン上の試みを削除または拒否する |
| **コンテキストの爆発** | 大きなリポジトリが無関係な読み込みでエージェントを溺れさせる | コンテキストは索引マップに沿った的を絞った検索と生読み込みで取得し、一括取り込みはしない |
| **本番で崩れるのに見逃されるレビュー** | 強力な2モデルが両方承認しても、実機インストールでは壊れる | smoke gateが使い捨てのアダプター側チェックアウトを作ってインストールし、結果を検証してからフェーズを進められる |

最後の行が、残り全部を正当化する理由です。エージェントによるレビューはロジックの誤りを見つけるのは本当に得意ですが、「そもそもインストールできない」ことに気づくのは本当に苦手です。だからこのハーネスは、エージェントの承認だけではフェーズを進めさせません。

## クイックスタート

RevHarnessはプロジェクトの**中に**インストールするものであり、その中で作業する前提のプロジェクトテンプレートではありません。一度クローンし、そこから実際にハーネスをかけたいリポジトリを指定します。

```bash
git clone https://github.com/sasuketorii/rev_harness_public.git
cd rev_harness_public

# 1. Confirm this machine can run it (non-destructive)
bash scripts/harness-doctor.sh

# 2. Install into your project
bash scripts/rev-harness install --target /path/to/your/project

# 3. Make one role-pinned agent call
echo "Summarize this repository's acceptance model." \
  | bash scripts/codex-wrapper.sh --role reviewer --stdin
```

`--target` を付けずに、ハーネスのチェックアウト自体の中で `install` を実行することは、意図的に拒否されます——ハーネスは自分自身のソースツリーにはインストールしません。

`install` は冪等(idempotent)です。既存の状態を保持し、足りない部分だけを埋めるので、再実行することが半端に設定されたチェックアウトを修復する通常の方法になります。

**macOSユーザーへ:** ハーネスにはbash 4以上が必要ですが、macOSにはbash 3.2が入っています。まず `brew install bash` を実行してください。これがインストール失敗の原因として最も多いものです。詳しくは [Requirements](getting-started/requirements.md) を参照してください。

一連の流れ: [Requirements](getting-started/requirements.md) →
[Installation](getting-started/installation.md) →
[First run](getting-started/first-run.md) →
[Daily use](getting-started/daily-use.md) →
[Troubleshooting](getting-started/troubleshooting.md)

## 推奨構成

ハーネスは手持ちの環境でも動きますが、実際にはこの構成で作られ、使われてきました。デフォルト値もこれを前提にしています。

### サブスクリプション

| プロバイダ | プラン |
|---|---|
| Anthropic | Claude Max 20x |
| OpenAI | ChatGPT Pro |

1系統ではなく2系統です。レビューゲートの価値は、レビュワーが実装者とは本当に別モデルであることから生まれます。すべてを1つのプロバイダで済ませると、儀式だけが残って恩恵のほとんどを失います。

作業を始める前に、両方のCLIをターミナルで認証しておいてください。ハーネスは認証情報を一切扱わず、各CLI自身のログイン状態に完全に依存します。

```bash
claude    # follow the login flow
codex     # follow the login flow
```

### 誰が操縦するか

**オーケストレーターはClaude Code経由でClaudeモデル上で動かす**——ターミナルCLIでもデスクトップアプリでも、どちらでも構いません。そこからオーケストレーターがClaudeとCodexの両モデルへ、必要に応じて呼び出しを行います。双方向に委譲できる1つの席を持つことが、系統をまたいだレビューを面倒な手作業ではなく実用的なものにします。

### モデル階層の割り当て方

| 作業 | 階層 | 理由 |
|---|---|---|
| 計画立案、調査、レビュー、リリースゲート | 利用可能な最強モデル | これらの判断は誤ると高くつき、実行頻度は低い |
| 実装スライス、ドキュメント、低リスクな編集 | より速く安価な階層 | 常時発生する作業であり、これに最上位階層の料金を払うと成果を改善せずにクオータだけを消費する |

この振り分けは、誰が打鍵しているかに任せるのではなく `.agent/registry/model_policy.json` に明文化されています。必要なときは `REV_HARNESS_CODEX_MODEL` で呼び出しごとに上書きできますが、上書きにも最低モデルの下限(floor)は適用されるため、レビューをこっそりポリシー未満に格下げすることはできません。

## 仕組み

5つの層があり、下にいくほど安定しています。

```
Layer 4  Smoke verification    real install into a throwaway checkout
Layer 3  Product code          src/ — what you are actually building
Layer 2  Project state         plans, evidence, run state, lineage
Layer 1  Harness               scripts/ + harness-rust/ + skills + hooks
Layer 0  Ground truth          rules, invariants, immutable project identity
```

受け入れ判定はLayer 0(決定論的チェック)**と** Layer 4(smoke run)の両方に根拠を持たねばなりません。どちらか一方だけでは不十分です——この非対称性こそが設計全体の核心です。

### ロール固定の呼び出し

すべてのエージェント呼び出しは、ベンダーCLIを直接叩くのではなく、ラッパーを経由します。3つのラッパーは互換ではありません——ベンダーCLIごとに「ロール」の概念が異なり、各ラッパーの `--help` が正本です。

```bash
# Codex: role fixes model tier + reasoning effort + web-search policy.
bash scripts/codex-wrapper.sh --role <coder|high-coder|reviewer|research|standard> --stdin < prompt.md

# Claude Code: NO --role flag. Deprecated passthrough shim (see below);
# pins --model/--effort explicitly and always requires --output.
bash scripts/claude-wrapper.sh --model opus --effort xhigh --output out.json "prompt"

# Cursor: role is one of Cursor's own official modes, not a Codex-style
# job role — ask (read-only, default), agent, or yolo (agent + auto-approve).
bash scripts/cursor-wrapper.sh --role <ask|agent|yolo> --stdin < prompt.md
```

`scripts/claude-wrapper.sh` は**非推奨の互換シム**です——呼び出すたびに `[DEPRECATED]` を表示します。Claude Codeへのcross-family呼び出しはClaude Agent SDK / Claude Codeサブスクリプションの利用枠を消費するため、ハーネスの既定オーケストレーションフローからは除外されています。代わりにTaskツールやClaude Codeネイティブのsubagentを使ってください(`docs/agent-sdk-policy.md`)。`--role` を渡してもラッパー自体は拒否せず、そのフラグはそのまま配下の `claude` CLIへ転送され、`claude` 側が `error: unknown option '--role'` で失敗します。

このラッパーはプロジェクトの識別子(project identity)を解決し、破損していれば実行を拒否し、model policyのハッシュを検証し、最低モデルを強制し、そのロールのreasoning effortとweb-searchモードを固定し、サンドボックス・承認・モデル・effort・searchを上書きしようとする呼び出し元の試みを削除または拒否し、呼び出しごとに1行のメトリクスを出力します。

Codexロールが何を変え、何を変えないかは正確に理解しておいてください。ロールが固定するのは**effortとsearch**です——`reviewer` は最高effortで動き、`research` だけがライブのweb searchを持つロールです。ロールによってサンドボックスを差別化する**ことはしません**——どのロールも `workspace-write` かつ承認オフで動きます。**reviewerは読み取り専用ではありません**。書き込みできないと当てにしないでください。

ベンダーCLIを直接呼ぶこと自体は問題なく動作し、上記のガードをすべて素通りします。これは意図的なトレードオフです——このハーネスは合意されたプロトコルであって、檻(cage)ではありません。

### Invariant(不変条件)

12個のinvariantは、誰でも自由に解釈し直せる散文ではなく、実行可能なチェックとして書き下されています——プライバシーゲート、証拠(evidence)の永続性、並列dispatch中の所有権宣言、スナップショットのハッシュ、facade/実装の分離、明示的な破壊的操作のオプトイン、そしてsmoke-gatedなレビュー要件です。それぞれが実行可能なコマンドに対応しています。正本(canonical)の一覧は
[`docs/canonical-invariants.md`](../canonical-invariants.md)(英語) にあります。

その強制力の強さは項目によって異なり、ドキュメント側にどれがどれかが明記されています。CIで本当にブロックするものもあれば、機械的に進行を止めるのではなく人間が読むための証拠を記録するだけのものもあります。この違いを軽視しないでください。

## 中身に何が入っているか

| 領域 | 内容 |
|---|---|
| `scripts/` | シェルスクリプト77本——ラッパー、ゲート、ライフサイクル、ガード。うち15本は `scripts/ci/` 配下 |
| `harness-rust/` | 3クレート構成: `agent-core`(lint と stamp サブコマンド)、`harness-cache`、`shared` |
| `test/` | テストスクリプト103本——ユニット41本、統合60本(加えて `test/integration/lib/` 配下の共有ヘルパー1本)、トップレベル1本。加えてbyte-pinnedなgolden fixtures |
| `docs/` | Getting started、運用マニュアル、ロール定義、invariant一覧 |
| `.claude/` `.agents/` `.codex/` `.cursor/` | ベンダーごとの設定、スキル、hooks、コマンド |
| `.agent_rules/` | すべてのエージェント系統が読む共有の運用ルール |
| `src/` | このチェックアウトでは空。ここで開発する場所ではない——下記参照 |

`.claude/skills/` には34個のスキルが入っており、これはエージェントがオンデマンドで読み込む再利用可能な手順書です。委譲(delegation)の規律、スコープガード、複数プラットフォーム向けのデプロイガード、言語別の知識パックなどをカバーしています。これらは `.agents/skills/` にもミラーされ、ベンダー非依存な利用者向けに提供されます。`.claude/skills/` が唯一の正本(single source of truth)であり、ミラーは自動生成されたものです。

## 既存リポジトリへの導入

RevHarnessは既存プロジェクトへ重ねる(overlay)ことを前提に設計されています。**この**チェックアウトの `src/` は単なるプレースホルダーです——`install --target <新規の空プロジェクト>` がグリーンフィールド用途でコピーする元になっているだけです。ハーネスのクローン自身の中で開発する場所ではありません。実際の、識別子と紐づいた `src/` はターゲットプロジェクト側に `install` が作ります。既存コードベースの場合はあなたのコードはそのままの場所にとどまり、ハーネスはその上に層として乗ります(`src/` はそもそも使いません)。詳しくは
[Installation](getting-started/installation.md#既存リポジトリへの導入) を参照してください。

`.agent/registry/rev_harness_distribution_manifest.json` にある配布マニフェストが、ハーネスが所有するパス、あなたのものであり絶対に上書きされないパス、そしてコピーではなく構造的マージが必要なパスを宣言しています。

## どこから来たのか

RevHarness は [CCTeam](https://github.com/sasuketorii/cc-team) の後継であり、2025年半ばから継続的に使われ、改訂され続けてきました。

この時期であることが、なぜこういう形になったのかを説明します。この系統の作業を始めた当時、**Claude Code にはサブエージェントがありませんでした。** 別のエージェントにタスクを渡す組み込みの手段はなく、ロール分離もなく、あるモデルが別のモデルの出力をレビューする仕組みもありませんでした。異なるモデル系統からセカンドオピニオンが欲しければ、配管は自分で作るしかありません——プロセス境界、プロンプトの受け渡し、成果物の授受、そしてレビュワーが本当に正しいものを見たのかを判定する手段まで。

そこでその配管が作られました。そして配管が現実の問題を捕まえ続けたので、次第に重装備になりました——ゲートが増え、invariantが増え、要求される証拠が増えました。そして重くなりすぎました——それに値しない変更にまで儀式が発火し、ハーネスが節約する以上の注意力を要求し始めたのです。だから削りました。意図的に、一度ではなく何度も。セマンティック索引は撤去されました。儀式は階層化され、些細な作業が重い作業のための保証を払わされることはなくなりました。サブシステムは保守されるのではなく、丸ごと削除されました。

いまあなたが見ているのは、そのサイクルの残渣です——実際の本番作業に対して、積み上げては削り落とすことを繰り返した結果です。ここで発明せざるを得なかったプリミティブのいくつかは、その後ベンダー自身が実装しました。サブエージェントは今やネイティブ機能です。コモディティ化していないのは、このリポジトリが実際に扱っている部分です——何をもって完了とするかを、機械的に決めること。

## なぜこれが存在するのか

エージェントはコードを書く速度を上げました。しかし*レビュー*を速くはしませんでした。そしてレビューは、1日あたりの注意力予算が決まっている人間が行うものです。

私たちはこの壁に直接ぶつかりました。アウトプット量がチームのチェック能力を上回り、明白な解決策——レビュワーを増やす——は、決してなくならないコストに対して線形にしかスケールしません。そこで実際のレビューが何を捕まえていたのかを見直したところ、答えは居心地の悪いものでした。**人間がチェックしていたことの大半は、機械的に判定可能でした。** テストが動いたか。止めるべきチェックが実際に止めたか。インストールされたものはレビューされたものと同一か。スコープは合意された範囲内にとどまったか。どれも判断力を必要としません。必要なのはゲートです。

そこでゲートを構築し、人間のレビュー予算は残りかす——設計判断、リスク判断、スクリプトが本当に決められないこと——に充てました。品質の下限は、疲れた人がたまたま気づくものではなく、機械が保証するものになり、人間が自分の目で見なければならない項目のリストは劇的に短くなりました。

証拠が不透明な内部状態ではなく**ディスク上の素のMarkdown**である理由もここにあります。2つのモデルが互いをレビューする場合でさえ、人間が入っていってファイルを開き、何が主張され何がチェックされたかを読み、異を唱えられなければなりません。ハーネスにしか解釈できない機械可読な状態では、その扉は閉じてしまいます。これらの成果物は、その場にいなかった人が読めるように書かれています。

## なぜ公開するのか——そしてなぜ自分たちでは使うのをやめたのか

この一文の両方が真実であり、何かを採用する前にその両方を知っておくべきです。

**なぜやめたか。** 私たちは多数のプロジェクトを同時に走らせています。ハーネスの改善は、既存のすべてのプロジェクトのコピーへ一つ一つ伝播させる必要があり、その移行作業はやがて、ハーネスが節約するはずだった時間のかなりの割合を食いつぶすまでに膨らみました。並行して、この「鎧」が強制していることの多くは、よく作り込まれたエージェントのアイデンティティ——ゲートに念押しされなくても発火するくらい強い操作上の本能——によって代替できることが分かってきました。この方向性は、はるかに軽い重量で似た地点に到達しつつあり、そのため今このハーネスは私たちの日々の運用ではありません。

**それでも公開する価値がある理由。** 私たちをここから押し出した経済性は、大きなポートフォリオを運用する場合に特有のものです。あなたが1人の開発者であれ、少数のサービスを持つ会社であれ、私たちを苦しめた移行税を払うことはありません——一度インストールすればそのまま動きます。何かが古びたり間違っていたりするわけではなく、私たちがその「形」を卒業しただけで、その中身が悪かったわけではありません。

公開しても安全です。このリポジトリは、私たちのツール群のうちバックエンドとシステム規律の半分にあたります。フロントエンドの知見と、より細かいバックエンドのノウハウは別の場所にあり、ここには含まれていません。

## 実際の価値

正直な売り文句は「コードが良くなる」ではありません。**操縦する人間の経験が浅くても崩れない品質の下限**です。

その対極を、あなたはすでに見たことがあるはずです。誰かがエージェントでサイトやシステムを作ったと発表し、数秒でエージェント製だと分かる——画一的な構造、もっともらしいが吟味されていない選択、その手のサイン。それが、無管理のエージェント出力が収束する先です。

私たち自身の仕事はその反例です。[company.rev-c.com](https://company.rev-c.com) と、社内システムUIライブラリのREVCNは、すべてAIによって書かれていますが、AI製には見えません。違いはモデルではありません。誰もが同じモデルを使っています。違いは、一方のワークフローには何をもって完了とするかを決めるハーネスがあり、もう一方には返ってきたものをそのまま受け入れる人間がいる、ということです。

だからこれを見て「ClaudeやCodexを直接使えばいいのでは」と思ったなら——それも可能で、何かは得られます。ただし、反対側から出てくるものは同じではありません。

## これができないこと

公開前に、この文書の過剰な主張を見つけるためだけに、Claude 1つ・Codex 1つの2つの独立したモデルレビューを実行しました。見つかったものは、こっそり文章を直すのではなく、ここに残してあります。

- **セキュリティ境界ではありません。** ベンダーCLIを直接呼ぶこと、証拠成果物を手で編集すること、状態ファイルを自分で書くことを止めるものは何もありません。OSレベルの分離はありません。この出力を改ざん耐性のある監査証跡として提示しないでください。
- **レビュワーは書き込みできます。** すべてのロールは `workspace-write` で動きます。ロールが変えるのはeffortとsearchであり、ファイルシステムへのアクセス権ではありません。
- **レビューチェックは形式を検証するのであって、著者を検証しません。** 指定された2つのファイルが存在し、判定(verdict)を含んでいることを確認するだけです。異なる2つのモデルがそれらを生成したこと、正しい差分をレビューしたこと、あるいは人間が両方を書いていないことまでは検証しません。
- **smoke gateはハーネスをテストするのであって、あなたのプロダクトをテストするものではありません。** 使い捨てのチェックアウトへインストールし、ハーネスのライフサイクルを動作させます。あなたのビルド、あなたのマイグレーション、あなたのend-to-endテストは、依然としてあなた自身が実行するものです。
- **モデル識別子は古びます。** floorチェックはバージョン番号を比較するだけで、そのモデルが存在するか、あなたのアカウントで使えるか、より優れているかまでは分かりません。
- **儀式のコストがかかります。** 2回のレビューには2回分の時間とトークンがかかります。短命なプロトタイプを作る1人の開発者にとっては、トレーサビリティの価値をそのオーバーヘッドが上回る可能性が高いです。
- **意見が強く入っています。** もっと軽い手触りが欲しいなら、ラッパーとtruth matrixだけ持っていき、残りは置いていってください。

強制されたレビュワー分離やコンプライアンス級の監査証跡が必要なら、このハーネスは今日それを提供していません。提供しているかのように採用しないでください。

## 意図的に外したもの

これは私たちが社内で運用しているものの完全な抜粋ではありません。**私たちの中核的な強みに相当するゲートとヒューリスティクスは、公開前に取り除かれています。** 具体的には、判断層——どの変更サーフェスでどのチェックが発火するか、リスクをどう分類するか、しきい値をどこに置くか、実際に何がまずくなるかについて蓄積されたルール群——は、長期間にわたって私たち自身の仕事に対してチューニングされたものであり、そのチューニングこそが商業的価値を持つ部分です。それはここにはありません。

公開されているのは骨格と仕組みです。ラッパー、受け入れ判定の契約、証拠フォーマット、smoke gate、ライフサイクル、invariant構造。これらは機能します。しかしゲートの良し悪しはそこに込められた判断力次第であり、これらのゲートの一部は、研ぎ澄まされた道具というよりも、よく出来たプレースホルダーに近い状態です。

**もし何かが期待通りに捕まえてくれないなら、たいていそれが理由です——直すのはあなたの仕事です。** これは想定された使い方であり、慰めの言葉ではありません。あなたの失敗モードは私たちの失敗モードではありません。他人のインシデントに合わせてチューニングされたハーネスは、そもそも間違ったハーネスです。移植できるのは形であり、その形こそがこのリポジトリです。

具体的には、次への投資を見込んでください。

- *あなたの*スタックにとって重要なチェックをtruth matrixに追加し、リリースゲートへ配線すること。
- リスク分類を締め直し、重い儀式が本当に危険なサーフェスで発火し、それ以外では邪魔にならないようにすること。
- smoke gateを拡張し、ハーネス自体のインストール・起動経路だけでなく、あなたのプロダクトのそれもカバーすること。

汎用的な仕組みを研ぎ澄ますプルリクエストは歓迎します。あなたのドメイン判断を共有層にハードコードするプルリクエストは歓迎しません——それはまさにあなた自身のフォークに置くべきものです。

## 知っておくべき歴史

RevHarnessはかつてセマンティックなコードインテリジェンス層を搭載していました——tree-sitterによるシンボルインデックス、プロジェクトごとのSQLiteインデックス、`sem.*` 取得ツールを公開するMCPサーバー、圧縮されたコンテキストカプセルです。これはオプトインのアドオンに降格され、計測期間を経たのち、完全に削除されました——削除された行数はおよそ42,900行です。`rg` を使ったエージェント的検索は、鮮度を保ち続けなければならない索引なしで必要なものを取得できました——そしてその鮮度維持自体が、コミットのたびに課されるfail-closedなサーフェスでした。

その完全な理由づけと、それでもセマンティック検索が欲しい場合にどうすればよいかは、
[Why there is no semantic index](architecture/why-no-semantic-index.md) にあります。
